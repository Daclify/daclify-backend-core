# Daclify community MCP

Local development package `0.1.0-alpha.4`: core `0.15.0-alpha.14`, modules SDK `0.10.0-alpha.21`, stable MCP server/client `2.3.1`. Native contracts are unchanged. The package is an immutable review artifact, not a registry publication or production qualification.

Install the three version-matched archives together (`npm install --ignore-scripts ./core.tgz ./modules.tgz ./mcp.tgz`). Generate public connection configuration through Daclify's AI connection page when that deployment advertises `community-mcp-local-v1`.

Run `daclify-community-mcp pair --config /absolute/public-connection.json --credentials /absolute/private-directory/delegate.json --socket /absolute/private-directory/companion.sock`. Approve the printed Daclify browser consent request with your existing account. The browser signs the bounded native delegate and a fresh account-control proof. The harness redeems its five-minute PKCE request once and encrypts the replaceable delegate/token under a password entered through a trusted terminal. Root keys and recovery kits stay in the browser.

Start `daclify-community-mcp serve --credentials /absolute/private-directory/delegate.json --socket /absolute/private-directory/companion.sock` in your trusted foreground terminal. It unlocks the `0600` encrypted delegate file through that terminal and serves the protected signer through a same-user `0600` socket in a `0700` directory. Keep this terminal running while the harness connects. Use the generated `bridge` command and socket reference in background or IDE harness configuration. No unlock password is available to the bridge. `status` and `revoke` also use a trusted controlling terminal. Stdout carries MCP protocol during serving/bridging. Never put passwords or keys in model prompts, arguments, environment variables or harness JSON.

The tool inventory is `list_daos`, `get_membership`, `list_activity`, `prepare_proposal`, `prepare_activity`, `prepare_vote`, `prepare_review`, `submit_signed`; the protected local signer additionally supplies `submit_prepared`. Hosted access does not receive that local tool. Tools exclude arbitrary transaction signing, private profiles/decryption, root administration and treasury operations. Proposal settings come from the DAO's current policy. Reviews require an independent current reviewer. Activity uses its separate approved app grant and configuration revision.

The shared producer validator checks current member, nonce, session expiry/epoch/revocation, guardian, role, policy and deployment before signing/submission. The service persists the exact protected native transaction first; missing responses reconcile the same ID in irreversible blocks before another event. Pairings, grants and preparation records have bounded cleanup and are covered by account deletion and both reconnection entry paths.

`revoke` invalidates the service token and removes this local file. Retire the matching native session through Daclify to disable independent delegate copies. Delegates are replaceable through fresh consent; no second account recovery kit is created. The capability matrix and exact browser/native/stdio/clean-install/harness evidence qualify supported combinations separately. These checks do not imply universal harness or hosted OAuth compatibility.

The `./http` export creates the real SDK stateless HTTP handler with an access resolver bound to each authenticated request. The API validates separate resource-bound OAuth first; the package does not treat SDK `authInfo` as proof by itself. Hosted HTTP supports read/prepare and external signed submission; a client without a native companion gets a `signer-required` preview. No private key or local signer enters this transport. See the versioned Daclify MCP guide for issuer/discovery/PKCE/rotation and exact preregistered client configuration.

The qualification matrix covers official SDK client/server `2.3.1` and Codex CLI `0.162.0-alpha.17.2` app-server MCP calls, over local stdio through the foreground companion and resource-bound HTTP OAuth. Codex inference turns, other harnesses, provider-managed secret stores and production HTTP deployments remain unqualified. HTTP clients use exact preregistered HTTPS callbacks or an explicitly configured fixed `127.0.0.1` callback; dynamic client registration is unavailable. The AI connection page exposes public configuration, immutable version-matched archive hashes and separate service/native-session revocation.
