# Encrypted On-Chain Profiles Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` inline. No delegation. Track checkboxes in the master ledger.

**Goal:** Keep profile contents on chain while limiting readability to the user and authorized people, with an honest recovery/deletion lifecycle.

**Architecture:** Encrypt in the trusted client using independent random profile keys. Store a bounded versioned encrypted current profile in the existing native profile record without changing its legacy serialization; a separate API key-envelope service stores only recipient-sealed envelopes. Ordinary recovery restores account keys and fetches surviving authorized envelopes, without a second kit.

**Tech Stack:** Existing Web Crypto AES-GCM/P-256/HKDF primitives, strict TypeScript/Zod, Antelope C++, PostgreSQL, Vue, Vitest/VERT/native tests and Playwright.

**Spec:** [Design](../specs/2026-10-12-self-service-mini-apps-and-account-exit-design.md); [master](2026-10-12-self-service-mini-apps-and-account-exit.md); [account continuity](../specs/2026-10-12-account-access-continuity-design.md).

## Global Constraints

Honor master constraints. Plaintext≤4,096 UTF-8 bytes; stored encrypted envelope≤8,192 UTF-8 bytes; at most 64 active key recipients including owner. Independent random 32-byte data keys, AES-256-GCM, 12-byte random IV, authenticated full context. No recoverable key envelope on chain or random data key in the permanent account kit. Existing plaintext history remains public; do not claim retroactive erasure or GDPR compliance. Recipient revocation affects future versions, not obtained copies. Keep existing DAO `EpochGrant`, `epochGrantDomain`, history/custody checks and signing keys intact; profile grants have their own domains and erasure lifecycle.

## Review Focus

1. Ciphertext/key envelope replayed across DAO/member/version/audience — P1/P2 rejects.
2. A recipient revoked before an update retains old keys — P2 rotates future versions and explains limits.
3. Profile-key service/backup lost, deleted or restored — P2 records availability and prevents silent recreation.
4. An old deployed profile reader encounters encrypted version 2 — P1 upgrade tests and capability gating.
5. Personal fields leak through public people/search/images/AI — P3 complete output tests.

### P2: Implement removable owner/recipient envelopes and recovery

**Files (core):** Create `services/api/src/profiles/keys.ts`, `services/api/src/profiles/routes.ts`, `services/api/src/profiles/jobs.ts`, `tests/profile-keys.test.ts`, `tests/integration/profile-keys.test.ts`, `docs/guides/profile-key-lifecycle.md` and reserved additive `migrations/NNN_profile_key_envelopes.sql`. Modify `protocol/profiles.ts`, `protocol/routes.ts`, `protocol/sign-in.ts`, `sdk/profiles.ts`, `services/api/src/server.ts`, `services/api/src/auth/recovery.ts` and relevant existing recovery tests. Reuse `services/api/src/auth/account-ownership.ts`. **Frontend:** modify `src/auth/session.ts`, `src/auth/vault.ts`, `src/api/client.ts` for the existing account-key/proof boundary; `src/auth/private-access.ts` retains its DAO grant planner role and is not a profile-key vault.

**Interfaces:** `ProfileKeyGrant = {version:1,context:ProfileContext,recipientEncryptionKey:EncryptionPublicKey,ciphertextCommitment:string,grant:EpochGrant}` where `EpochGrant` reuses the existing shape with **profile-specific** authenticated domains, not DAO grant access. Its profile schema restricts salt to 32 decoded bytes, IV to 12 bytes and encrypted key/tag to 48 bytes; the general content envelope's large-file bound is not accepted here. SDK `sealProfileKey(key,recipient,context,commitment): Promise<ProfileKeyGrant>` and `openProfileKey(grant,recipientPrivateKey,expectedContext,expectedCommitment): Promise<Uint8Array>`. `ProfileKeys.put(ownerAccountId,grants): Promise<void>`, `.get(recipientAccountId,context): Promise<ProfileKeyGrant>`, `.remove(ownerAccountId,context): Promise<KeyDeletionStatus>`, where `KeyDeletionStatus.state` is `removed|backup-expiry-pending|unavailable`. Proposed `POST /v1/profiles/keys/share` with `{context,grants}`, `POST /v1/profiles/keys/remove` with `{context,ciphertextCommitment}`, and `GET /v1/profiles/:daoId/:memberId/keys/:profileRevision`. Extend `AccountControlPaths` for both literal POST writes; the existing proof hook binds their exact serialized body, origin/audience/session and actual account control. Verify native profile ownership independently; a request cannot assert arbitrary recipient ownership.
