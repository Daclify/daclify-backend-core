# Account Exit and DAO Closure Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` inline. No delegation. Track each checkbox and actual evidence in the master ledger.

**Goal:** Let a user leave one/all DAOs and delete their Daclify user, offering sole-member DAO closure while preserving claims, continuity and truthful cleanup status.

**Architecture:** New native departure/retirement actions preserve existing member/DAO serialization and financial records. A PostgreSQL leased workflow coordinates signed native operations, hosted personal-data cleanup and independent-app notices. Frontend confirmation separates leaving, closing and hosted-account erasure instead of treating them as one transaction.

**Tech Stack:** Antelope C++/VERT/native fixtures, TypeScript/Fastify/PostgreSQL jobs, canonical SDK/routes, Vue and Playwright.

**Spec:** [Design](../specs/2026-10-12-self-service-mini-apps-and-account-exit-design.md); [master](2026-10-12-self-service-mini-apps-and-account-exit.md); [account continuity](../specs/2026-10-12-account-access-continuity-design.md).

## Global Constraints

Honor master constraints. Ordinary members sign their own departure. Keep financial claims/stake and once-only settlement; no implicit transfer, burn, donation or provider cancellation. Sole-member closure is offered, never silently performed. Hosted data erasure may complete while a native exit remains unresolved. Missing successors or funds do not justify retaining all account fields indefinitely. Preserve migration 041's canonical/retired ownership relationship; add erased-account transitions in a later migration. Reuse implemented private-access planning/local verification and separately report recorded grants, verified client decryption and human recovery confirmation.

## Review Focus

1. Final administrator/controller departs with outstanding liabilities — X1 rejects unsafe closure, preserves settlement rights.
2. An erasure worker crashes after a chain submit or loses its lease — X2 reconciles before retry.
3. A retired account alias or old backup resurrects login/profile access — X2 handles every owned alias and restore exclusions.
4. A user deletes hosted credentials before receiving a usable exit/claim report — X3 preserves narrowly scoped status/settlement access.
5. A disconnected mini app claims cleanup or replays another app's notice — X4 verifies scope and reports evidence limits.

**Interfaces:** Proposed native actions `leave(runtime: name,dao_id: uint64_t,member_id: uint64_t)`, `startclose(runtime: name,dao_id: uint64_t,member_id: uint64_t)` and `closedao(runtime: name,dao_id: uint64_t,member_id: uint64_t)`. Dispatch only through current signed actor paths. Add one separately serialized `daolife` row per retiring DAO, keyed by DAO ID, containing state and transition time; missing row means active. `DaoLifecycleSchema = 'active'|'closing'|'closed'`. Gateway methods use producer instructions, never forge member authority.

**Private handover interface (new, not in the pushed release):** Native `beginhand(runtime,dao_id,member_id,departing,successor,expires)` is administrator-authorized; `scanhand(runtime,dao_id,member_id,limit)` scans at most 25 committed epochs; `accepthand(runtime,dao_id,member_id)` requires the selected successor's own native/root authorization; `clearhand(dao_id)` erases the single record only after expiry. Runtime/DAO/member/departing/successor types follow the existing action conventions (`name`/`uint64_t`); expires/limit are `uint32_t`, with expiry at most 3,600 seconds ahead. One `handovers` row per private DAO stores initiator, departing/successor IDs, their credential epochs, successor encryption-key hash, current DAO key epoch/history policy, last recorded epoch, scan cursor, completed/accepted flags and expiry. No variable data or new secondary index; use the existing member/epoch grant index. Core owns `DaoHandoverSchema`, derived from the generated row plus `pending|ready|expired|stale` status; `ChainGateway.privateHandover?(daoId: string): Promise<DaoHandover | null>` and `GET /v1/daos/:id/handover` expose it without secret key material. Null means no preparation; missing capability means unsupported, never ready.
