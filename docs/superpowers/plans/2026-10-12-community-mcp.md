# Community MCP Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use `superpowers:executing-plans` inline. No delegation. Track checkboxes and qualify both transports separately.

**Goal:** Let communities connect a supported AI harness to human/mixed or guarded-agent DAOs without owner intervention or exposing root keys to models.

**Architecture:** A reusable tool layer consumes public Daclify SDK/schema artifacts. Local stdio uses a protected community signer and self-service browser pairing; hosted Streamable HTTP uses dedicated resource-bound OAuth and accepts only permitted externally signed submissions. Native scope/guardian/role checks remain authoritative on every operation.

**Tech Stack:** Node 24.21.x, strict TypeScript/Zod, stable `@modelcontextprotocol/sdk@1.32.1`, existing Fastify/PostgreSQL API, canonical Antelope instruction codecs and actual native fixtures.

**Spec:** [Design](../specs/2026-10-12-self-service-mini-apps-and-account-exit-design.md); [master](2026-10-12-self-service-mini-apps-and-account-exit.md); existing [agent cooperative design](../specs/2026-10-11-agents-only-service-cooperative-design.md), limited to its credential/guardian principles rather than its commercial platform.

## Global Constraints

Honor master constraints. No arbitrary SQL, transaction signing, root administration, withdrawal or autonomous private-content disclosure tools. A human's assistant is not automatically an enrolled agent. Member routine sessions and Activity app sessions retain distinct native scopes, seven-day maximum expiry and 16-session/member limit. Local pairing does not relax existing app HTTPS callback validation. MCP dependencies belong in a separate package, not the restricted core protocol package. Existing account reconnection preserves the native keys/member and revokes hosted sessions/app tokens; require fresh MCP authorization on that transition, without pretending SQL reconnection itself revokes native signing grants.

## Review Focus

1. Tool argument/model prompt changes DAO/action/payout fields after preview — M1 signer revalidation.
2. Guardian pause/revocation/expiry occurs between discovery and submit — M1/M2/M4 current native checks.
3. Harness leaks signer credentials or reconnects using another member — M2 protected keystore/pairing tests.
4. A hosted client presents app tokens, wrong audience or reused OAuth code — M3 rejection.
5. Remote-only or unsupported harness is advertised as able to sign — M4 explicit capability matrix.

### M3: Add dedicated MCP OAuth and hosted Streamable HTTP

**Files (core):** Create `services/api/src/mcp/oauth.ts`, `services/api/src/mcp/routes.ts`, `services/api/src/mcp/http.ts`, `tests/mcp-oauth.test.ts`, `tests/integration/mcp-http.test.ts`; modify `protocol/mcp.ts`, `protocol/routes.ts`, `services/api/src/server.ts`, `services/api/src/auth/account-reconnect.ts`, `tests/integration/wallet-recovery.test.ts`, current account-exit inventory and the reserved pairing migration before publication (otherwise a new additive OAuth migration). Create `packages/community-mcp/tests/http-client.test.ts`; update the MCP guide and frontend connection configuration UI.

**Interfaces:** Remote MCP endpoint `/mcp`. `createMcpHttpHandler(deps: McpHttpDependencies): McpHttpHandler` adapts the stable SDK Streamable HTTP server transport to existing Fastify without adding another web framework. Core owns dedicated `McpOAuthClaimsSchema` including resource audience, account/member/DAO binding, bounded scopes and expiry. Scopes: `daclify:read`, `daclify:prepare`, `daclify:submit`. Discovery uses RFC 9728 protected resource metadata for the canonical `/mcp` resource and authorization-server metadata for issuer `<api-origin>/mcp/oauth`; authorize/token paths live under that issuer. Existing app OIDC remains separate/compatible.

- [ ] Write actual SDK HTTP client tests: unauthorized calls discover the correct resource/authorization metadata; PKCE S256 and exact registered redirects work; code reuse, CSRF/state substitution, missing/wrong resource, wrong audience, excessive scope and arbitrary app tokens fail. Primary requirements are the [MCP authorization specification](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization), [stable SDK server documentation](https://ts.sdk.modelcontextprotocol.io/server) and [security guidance](https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices).
- [ ] Implement resource-bound consent/auth code/token flow through existing account reauthentication and current membership/role policy.
