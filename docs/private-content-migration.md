# Upgrade existing DAO descriptions to private content

This optional, signed upgrade preserves DAO IDs, original keys, membership, roles, admission policy, balances, outstanding payments and existing ballot definitions. Earlier public transactions, files and recipients' copies remain readable.

## Review and apply

1. In an encrypted DAO's settings, open Identity and choose **Review privacy upgrade**. Reviewing reads records without signing or publishing.
2. Review the proposed replacements and historical disclosure notice. Each page contains at most 25 items. A cursor identifies the next page; it grants no authority.
3. Unlock the original account through an already qualified full-access method. A paired wallet can authorize supported public actions without possessing the original document key. Sign-in alone cannot recreate that key; use an unlocked original device or its encrypted recovery kit when required.
4. Approve a reviewed item. The browser encrypts its content, verifies its exact published document, then signs the attachment. Success requires a verified attachment.
5. Review remaining records again. Old ballots and immutable agreed payroll terms keep their original meaning. Payroll migration changes only the display name. Public branding needs a new encrypted upload in the private identity editor; its old public CID cannot become confidential.

Managed-allowed admission continues to permit operator-assisted recovery. An operator able to recover a reader's keys may read content shared with that reader. This upgrade neither tightens admission nor enrolls recovery.

## Interruptions and key changes

Retry first. The interface reconciles the original upload receipt and native parent before another signature. Local drafts contain technical IDs, commitments and stages rather than descriptive plaintext or private account keys.

If an epoch or reader set changed before attachment, explicitly choose the offered re-preparation action and review its successor. It requires original grants and keeps the same logical ballot or payroll ID. Unopened definitions may get a new protected revision; committed definitions are never rewritten. An expired payroll start needs a newly reviewed time, preserving amount and recipient.

An uncertain upload must resolve to its exact verified receipt or an authenticated unknown-request result before replacement. The original encrypted local upload survives until its successor is ready. The service tracks older verified requests; the browser keeps the latest 25 IDs. Re-preparation does not delete files or release their billed allowance. Missing source bytes, original grants or supported formats block progress without creating replacement account keys.

## Archives and deployment

Referenced versions remain retained while rights require them. Pruning requires existing archive verification, retention, coverage and signed approval. Restoration must reproduce the original committed row. New keys alone cannot decrypt it. See [archive exports](archive-exports.md) and [disaster recovery](disaster-recovery.md).

Installing shared code and adopting module pins for a DAO are separate operations. Qualify the exact runtime, modules, SDK and archive decoders together. Preserve historical source identities. Inventory pending governance targets, source pins, lifecycle sources and obligations before adoption; do not rewrite frozen targets or silently approve customer migrations.

TESTDAO-2 (`1551563545746804138`) remains unchanged until its owner unlocks the original keys and deliberately signs its reviewed upgrade. The [Telos EVM proposal](proposals/2026-10-16-telos-evm-privacy.md) remains separate and disabled. Participation, ordinary vote choices, roles, thresholds, amounts and transaction graphs remain public.
