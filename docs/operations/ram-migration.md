# Legacy RAM migration — development qualification

The full backfill controller adopts an **unobserved** legacy runtime. Already observed deployments use the separate completion-only sequence below. Neither sequence is an automatic production upgrade. Do not reset counters, re-run `initramobs`, rewrite accepted code pins, or reuse this sequence over a populated observer. Keep the original release artifacts and signing/encryption domains.

## Before starting

Inventory every DAO, installed module and pending executable approval. Back up the chain projection, original contract artifacts, provider ownership ledger and private recovery material using the existing backup procedures. Review the exact current runtime/module code and ABI hashes. Unsupported third-party contracts are outside this migration. All supported module payers must belong exclusively to this runtime: `bindrampool(runtime)` requires the payer's own authority and permanently binds it. Binding a payer still serving another runtime is unsafe.

Drain pending executable approvals before changing their pinned contracts, or use a separately reviewed, DAO-approved migration. Decide's `checkmig` refuses an unexpired open or approved plan whose Works/Grants code changed. A finalized failed vote cannot execute and does not block replacement until its former deadline. The guard reads the authoritative ballot, checks its DAO domain, and refuses missing ballot state; it does not reinterpret a failed vote as approval. No action here changes its approved hashes or commitments. Module kind is checked by actual module code; a wrong kind aborts `beginram` atomically.

Purchase enough actual native RAM for the existing state, scan cursors, temporary protected-write overlays, legacy financial holds and platform headroom **before** maintenance. Configured byte values are not funding. Preserve a reconciled baseline for code, permissions and external system/token rows. There is no unlimited maintenance reserve.

## Bounded sequence

1. Deploy the reviewed, compatible artifacts under operator authority after the pending-work review. This runbook does not authorize deployment.
2. Call `beginram(sources)` with at most five explicit `{account,kind,code_hash}` entries. Kinds are Decide=1, Works=2, Payroll=3, Grants=4 and Endorsement=5. Every installed module must appear with its existing accepted hash. Beginning twice rejects.
3. Call `scanram(0,table,limit)` for every global family, and `scanram(dao_id,table,limit)` for every scoped family in canonical `contracts/common/ram_families.hpp`. Limit is 1–25. Resume until that family's `ramcursors` entry is complete. Scan empty families too; an absent cursor cannot certify coverage. Key zero is included and uint64 maximum does not overflow.
4. On every module, call `scanram(runtime,table,limit)` for `rampayer` and every family returned by the canonical module-kind list. Decide additionally scans `adoptelect` and `adoptpolls`: they allocate missing election term holds and missing ordinary-poll completion markers. Works scans `adoptwork` to reserve missing fixed submission/review reference slots for pending accepted milestones. Payroll scans `adoptpay` to create missing fixed settlement controls without changing schedules. Terminal legacy poll markers start their retention clock now; the old ballot close time is not a fabricated completion timestamp.
5. Call `adoptram(dao_id,false,limit)` until `adoptobs` is complete, then `adoptram(dao_id,true,limit)` until `adoptclaims` is complete. This also creates missing default human credential rows, matching the legacy absence/epoch-1 semantics without rewriting members. It reserves receipt RAM for pending obligations and a separate `ramclmholds` row for an existing claim without a ready hold. A separate table avoids colliding with future obligation IDs. Run/complete the ordinary family scans for these new tables too.
6. Call `sealram(limit)` in batches of 1–5 DAOs. It requires complete core/module/adoption coverage, stable source hashes and unchanged installed code pins. Incomplete batches roll back. A completed retry is harmless. API RAM totals remain unavailable while the migration is active.
7. Reconcile all six native payers against DAO/platform counters and observer metadata. Set physically backed payer pools with their reviewed baseline and headroom. Call `inheritram` once per DAO/payer with explicitly approved additional activity/identity/completion headroom; completion headroom is at least 32 KiB. It snapshots occupied legacy bytes and uses the existing backed grant path. Exact retries do nothing; changed retries reject. This creates a capacity attestation, **not** a historical invoice or payment.

Ordinary insert/growth/pruning is blocked during migration. Fixed-size updates and explicitly bounded completion/recovery table operations preserve their original authorization and are captured before the scan when needed. Protected mutations still need physical RAM; migration is not a promise that an unfunded legacy claim can complete before its hold has been adopted.

## Remaining rollout gates

Per-DAO quota release qualification, complete supported-old-release lifecycle qualification, external token row-payer reconciliation, live provider funding and the immutable release packet are separate work. These actions do not enable quotas, buy provider services, collect payments, prune history or unpin files. Public rollout remains gated until the required evidence exists.

After reconciled backed allocations, explicit operator `setdaoquota(dao_id,true)` can enable the development growth guard. It is not part of the migration sequence or API startup. Do not enable it publicly before all required completion/recovery and release checks pass. See [enforcement bounds](../ram-accounting.md#per-dao-growth-enforcement--development-qualification).


## Already observed deployments: completion adoption only

Keep the original counters. Do not call `beginram` or scan ordinary RAM families: their historical rows have already been counted. Drain old code-pinned executable approvals before replacing module code, retain the old artifacts, and explicitly rebind the observer to the reviewed core hash. Update source and installed module pins only under their existing operator/DAO authorization; adoption never rewrites executable plans.

With each affected DAO's quota guard disabled, call `adoptram(dao_id,false,limit)` until `oldobs` completes, then `adoptram(dao_id,true,limit)` until `oldclaims` completes. Batches are 1–25. Only missing obligation holds, credential rows and legacy claim holds are created; existing rows and counters are not rescanned. The cursor metadata is platform overhead. Complete retries do nothing.

For current first-party modules call `scanram(runtime,table,limit)` only for their completion families: Decide `adoptelect`/`adoptpolls`, Works `adoptwork`, Payroll `adoptpay`. These actions require runtime authority and qualified current source code. They allocate only missing reserves or fixed references and preserve original ballot/project/schedule records. Updating a source with an unexpired executable approval is not covered by this procedure: drain it with its original approved code first.

Reconcile actual native usage, fund every physical payer, and establish reviewed pools and inherited allocations before enabling a guard. `setdaoquota` requires credentials for existing members, ready physical reserves for claims, pending-obligation reserves and every installed module's `checkquota`. Works checks accepted-work reference slots, Payroll checks settlement controls, and Decide checks active election reserves and open ordinary-poll completion markers. An unknown module lacking this action fails activation atomically. Activation currently bounds each core family/DAO-indexed module scan to 5,000 rows; Works uses the existing DAO project index and bounds the target DAO’s referenced milestones to 5,000 rows. Other DAOs’ milestones do not block activation. Larger histories need a separately qualified bounded activation method. Do not evade this limit by deleting financial or active state.

These preconditions reduce upgrade risk; they do not qualify external token-row ownership, live providers or a public release. An owned native drill uses actual historical core, Works, Payroll, Decide and Grants binaries, preserves liabilities and rows, reconciles all five payers before exit, and exercises old-claim adoption, quota exhaustion, original-key recovery and full withdrawal. A failed historical award remains unchanged, no longer blocks the migration check, and still cannot execute. The complete supported-release lifecycle and other historical combinations remain release gates.

Reproduce the observed native drill with `npx tsx tools/build/observed-upgrade.ts`, then `npm run test:native -- tests/native/ram-observed-upgrade.test.ts` against the exact owned resource fixture. Configuration that predates observation is native baseline, not DAO usage. `inheritram` accepts either sealed full backfill or complete `oldobs`/`oldclaims` stages; it still requires reconciled funded pools and an unused permanent inherited grant.

The compiled historical Works and Grants drain regressions demonstrate the approved-code sequence: unchanged code can execute the original plan; replacement while pending is rejected by `checkmig`/execution without altering its saved hash; executing against the original producer then permits replacement. Grants fixtures create rounds, applications and approved plans with actual historical Decide/Grants/Works binaries, test each award producer's replacement independently, and complete once-only settlement under current Works code. Rebuild them with `npx tsx tools/build-document-upgrade.ts` in the modules repository, then run `npx vitest run tests/grants.test.ts tests/governed-works.test.ts`. Finalized failed votes are separately checked without modifying their plans or treasury. These are qualification examples, not permission to execute a real DAO’s pending proposal.
