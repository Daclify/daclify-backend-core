# Names pricing and payment review

Names profit policy version 1 adds current provisioning costs to a minimum net margin. Existing serialized records remain compatible; suffix offers and dotted exact listings are subject to the current basic-account floor. The testnet basic package is 30720 RAM bytes, 0.5000 TLOS CPU and 0.5000 TLOS NET; the minimum margin is 100 USD cents.

The API and native contract calculate RAM from the current system market, including RAM fees and conservative integer rounding. CPU and NET stakes are added in TLOS base units. A fresh Delphi TLOS/USD observation converts the resource cost upward to USD cents. Native payment adds the configured conversion premium to resource cost plus margin. Card payment grosses that subtotal up for its fee allowance. USD and native amounts are separate totals, not equivalent conversions of a single card total.

The initial Spain standard-card allowance is 515 basis points (3.15% international plus 2% currency conversion) and €0.25 converted upward using a dated ECB USD reference. This estimates a price; it does not prove the fees actually charged. Sources: [Stripe Spain pricing](https://stripe.com/es/pricing), [fee retrieval](https://docs.stripe.com/expand/use-cases), [balance transactions](https://docs.stripe.com/api/balance_transactions/object), [ECB references](https://www.ecb.europa.eu/stats/policy_and_exchange_rates/euro_reference_exchange_rates/html/index.en.html).

Checkout is restricted to cards and USD with Adaptive Pricing disabled. Fulfillment retrieves the paid Checkout Session, succeeded PaymentIntent, captured charge and its balance transaction. It verifies mode, metadata, identities, paid amounts, currency, fee/net conservation, source and absence of refunds/disputes. EUR proceeds use Stripe's recorded exchange rate; all conversions round net income down and fee costs up. USD and EUR balance currencies are supported. Missing asynchronous fee data returns a retryable 503 without creating an account.

`fulfillnet` requires the configured settler's verified gross and net USD amounts for every first-party card purchase. Gross-only `fulfill` cannot fund nonzero resources. Third-party cards are refused by the contract until seller routing exists. Native purchases must match the current exact TLOS price. Both rails stage a transient balance guard, create the account and provision resources, then run self-authorized `checkprofit` to measure actual token spending before any payout. Deposits during the entire sequence cannot conceal costs. A margin below the policy rolls the transaction back, including payouts, receipts and account creation.

For a third-party native sale, the fee is the configured percentage of the full incoming price, rounded down to TLOS base units. Seller proceeds equal incoming price minus actual RAM and CPU/NET spending minus that fee. A $10 sale with $2 of resources and a 5% fee allocates $2 to resources, $0.50 to Daclify and $7.50 to the seller. No resource charge is added to the buyer's advertised total. A payment below resources plus fee fails with `NAME_COST_LOW`, without borrowing from the reserve. Incoming native payment also funds first-party resources; all remaining first-party proceeds go to the treasury, with the first-party rate applied to the remainder for bookkeeping.

The existing `sales` and transient `profitcheck` layouts remain unchanged. New settlements additionally write `saleprov` version 1 with resource spending, seller proceeds and card net/cost allocations. Native `platform_fee` records only commission; native `platform_cents` is zero because `usd_cents` is an informational reference. Self-authorized `closepay` verifies the final native balance and clears the guard after payouts. Only settled state 2 survives a successful transaction. Missing sidecar receipts identify legacy sales, which keep their original accounting meaning.

## Observation command

Run `DACLIFY_ENV_FILE=<private testnet env> npm run price:names -- testnet` to print unsigned supported actions. Add `--apply` for the narrow testnet operator update. It verifies chain identity, runtime ABI/code, Names code and operator authority. It can refresh TLOS observations and the fixed-fee allowance; it preserves the margin, fee basis points, tiers, parties and all account authorities. It does not deploy code or transfer tokens.

The user service runs this every five minutes. TLOS observations expire after 900 seconds. ECB references may span weekends/holidays and expire after seven days. ECB failure preserves the previous allowance while continuing native updates; once the allowance expires, card quotes disappear while native checkout remains available. Previously paid card orders still use actual net proceeds and current resource costs.

## Paid order on hold

A checkout receipt means payment was captured; it does not mean the native account exists. Stripe retries temporary webhook failures. If verified proceeds cannot cover the required margin, creation stays unfulfilled and requires operator review through the original Stripe receipt. There is no automatic extra charge or automatic refund in this change. A support operator must reconcile the Checkout Session, captured charge, balance transaction and `sha256(checkout_id)` native sale reference before any refund or retry. Contract sales are authoritative for once-only fulfillment. Confirm the account and its recorded owner/active keys before telling the buyer creation completed.

The guard measures margin at provisioning using the observed TLOS/USD value and captured processing fees. Later chargebacks, refunds or asset price changes require separate reconciliation; they cannot be guaranteed by an atomic creation transaction. Native purchases restore the exact starting reserve balance, and can succeed with no starting reserve if the incoming payment covers all outlays. Card proceeds cover costs in fiat, but provisioning still spends TLOS working capital. No automatic fiat-to-TLOS conversion or reserve replenishment is implemented. No reserve transfer is part of this upgrade.

## Suffix account floor

Suffix registrations, updates and dotted exact-name listings reject each supplied nonzero price below the current basic quote on that rail (`NAME_PRICE_FLOOR`). Zero still means an unset rail. Basic pricing uses the same live resource estimate, TLOS observation, margin and card-fee allowance as first-party creation. Native and USD minima are separate. A missing basic price or stale conversion evidence cannot authorize a cheaper suffix registration.

At fulfillment, older offers use the higher of their stored seller price and the current basic quote. USD-only suffixes first apply the USD floor, then retain their native conversion rule. A native transfer must equal the effective quote; an old low quote rolls back without a payout or account creation. Each successful suffix sale raises the effective charged price, preserving unset rails. A stale fee reference disables new USD quotes while explicit native offers continue. Previously paid first-party cards still require verified net proceeds and current resource coverage. Stored inventory rows are seller reference prices; request a fresh quote for the amount payable.

This rule preserves provisioning tiers, seller authority, treasury destinations and the third-party fee share. It sets a minimum selling price; it does not extend the first-party $1 net-profit guard to third-party revenue. Third-party card checkout remains disabled until seller merchant routing is implemented. Undotted premium listings retain their existing price rules.

## Testnet settlement qualification

`node --import=tsx tools/deploy/names-settlement-testnet.ts` uses the private testnet configuration and deployment key files on this server. It pins the chain and prior code, compares all existing ABI layouts, and signs read-only `compute_transaction` checks for third-party allocation, first-party purchases, an empty native reserve, captured card net and rejected underpayments. It does not publish a listing or create an account. `--live` checks the installed build. `--apply` performs only the already qualified code/ABI upgrade; it requires the pinned prior code and verifies irreversible confirmation, unchanged inventory, authorities and reserve. The upgrade needs no RAM purchase or token transfer.

The Names build uses CDT 4.1.1 with `-O=s`, also recorded in `tools/build/contracts.ts`. The current audit candidate has a 91,743-byte Names WASM; its read-only simulation fits the observed testnet allocation. Core/protocol and frontend 0.11.0-alpha.2 mark the incompatible economic behavior; modules SDK 0.9.0-alpha.13 pins that producer while retaining contract version 0.9.0-alpha.5. Legacy action/table encodings are unchanged; new `closepay` and `saleprov` are additive. Current artifacts are core/frontend 0.13.0-alpha.3 and modules SDK 0.9.0-alpha.19. The earlier names-settlement command pins its historical baseline and must not be reused for the current candidate; use [audit remediation](project-audit-remediation.md). These are development artifacts, not a production release.

## Seller inventory and RAM

An ordinary 12-character undotted name is always first-party: `regname` and `editname` reject it, and legacy invalid rows cannot override an offer. Existing sales, pending orders and receipts remain intact. Exact special-name and suffix registrations charge the authorizing seller’s RAM; editing a legacy row moves its payer to that seller. The catalogue is paginated independently for exact names and suffixes, while an exact quote remains available beyond the first page. Stored inventory prices are references; request a fresh quote before payment.
