# Assisted profile recovery and refresh continuity

The reported email verification was followed by a gateway 504 from `/v1/account/recovery/claim`. Read-only live database metadata established an application-level lock cycle: recovery held the account row in a transaction, while its membership projection used another pooled connection to insert a membership with a foreign key to that locked account. A second membership refresh queued behind the same lock. This explains the blocked unlock and delayed connection error without evidence of an initial automatic browser reload or API restart.

The assisted-recovery policy check now passes its existing database connection to `NativeChainGateway.memberships`. This covers assisted setup, enrollment and claims through the same shared method. Account/grant/session locks, historical strict-private policy checks, origin/account binding and rollback of failed grant consumption remain intact. No key, policy or ownership records are changed by the fix.

The frontend retains memberships when a routine same-account, same-network session/membership refresh fails temporarily. The existing error/retry indication remains. Confirmed authentication loss, identity changes and domain changes still clear the relevant state. Keeping the profile identity stable prevents the embedded account editor from being unmounted and discarding its draft. This retained display data does not authorize actions; the API and contracts retain authorization.

The strengthened integration test uses real PostgreSQL foreign keys and the actual native membership projection, with controlled chain RPC rows and a disposable cryptographic custody provider. It first fails with HTTP 503 under a 500 ms test-only lock timeout, then passes after the shared-connection correction and decrypts the original disposable account keys. It also verifies the membership row commits. Existing replay, concurrent claim, assisted opt-out, unavailable storage, identity and strict-private tests remain part of the authentication/recovery suite. The frontend regression first fails because memberships are cleared, then passes when they are retained. A browser scenario covers an embedded profile unlock followed by a failed membership refresh and a further failed retry while retaining an unsaved draft.

API implementation 0.15.0-alpha.34 and frontend 0.15.0-alpha.53 preserve public protocol/SDK 0.15.0-alpha.32, modules 0.10.0-alpha.42, native code/ABIs, database schemas, service configuration, session/key timers and custody permissions. No dependency versions change.

Live intervention: terminating the specifically identified idle transaction to release its lock exposed an unhandled PostgreSQL client connection error and caused one automatic API restart at 16:47:37 UTC. It recovered by 16:47:46; portal/API returned HTTP 200 and the database had zero blocked queries. This intervention-caused restart is distinct from the original incident. No further connections were terminated. General database-disconnection resilience was not changed in this focused fix.

No real user's verification code, private key, recovery backup or decrypt operation was used. Production/mainnet and Almaiso were not changed. Controlled test success does not establish that the user's next live email recovery succeeds; that final account ceremony still needs a user retry after rollout.
