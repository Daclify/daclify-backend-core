# Hosted MCP approval with paired accounts

13 October 2026. Testnet now accepts a recent paired sign-in or an account-paired native/EVM wallet for hosted MCP consent. The compact card no longer requires an unlocked Daclify vault for this approval. Core API `f898bfea161b5a4b54cb023e612d93d91b772f96`, modules SDK `e69b1b927505959c57eb0f3c165ac80489864109` and frontend `5e019404399de055c4e3b7157bd62e7a389d1c0a` are pushed to `dev`. Genuinely clean detached candidates serve testnet. [Exact delivery evidence](2026-10-13-paired-mcp-approval.json) records artifacts, test/report hashes, initial failures and held external checks.

The user confirmed that either a paired blockchain wallet or a paired login should approve this connection. The previous card reused DAO-action signer readiness, which required a usable DAO signer even though the API already accepted account-paired native/EVM approval. It now has a dedicated **Approve with** selector: paired sign-in, Daclify keys, Telos Zero wallet or Telos EVM wallet. Wallet readiness checks the account's verified links and connected wallet identity. No DAO wallet activation or binding is performed by the card.

Paired sign-in consent requires authentication within five minutes, an unexpired/unrevoked matching session and a credential still paired to that account. The backend verifies Google/Telegram/email, passkey or wallet provenance against its current stored link. A resumed cookie does not renew authentication. Stale sign-ins renew inside the card using the existing verified methods; a different account is rejected. The browser still obtains a fresh single-use intent bound to the exact body, account, session, origin and API audience. The new proof is accepted only for `/v1/mcp/oauth/approve`. Native delegation, credential changes, key sharing, recovery and erasure retain their existing proof requirements.

Hosted submission still requires an existing approved matching local signing companion. Without one, consent issues read and preparation scopes only. The remote client receives no Root/private-profile keys, decrypted profile or vault unlock capability. Desktop/mobile tests approve and renew with a genuine disposable email-code login while the vault stays locked, exchange the narrowed token and refuse authorization-code replay.

The optional Google button uses Google's GIS callback with a fresh nonce and bounded credential validation, and appears only when its public client ID is configured. Actual testnet configuration currently has **Google unconfigured**, Telegram configured, email delivery `mail` and a passkey relying-party ID. Configuration and fixtures do not qualify actual provider/device prompts. No live Google, Telegram, email delivery, passkey or wallet prompt was run in this follow-up.
