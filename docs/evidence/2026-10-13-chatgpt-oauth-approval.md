The user's real connection reached ChatGPT's connection window, then Daclify's authorization endpoint returned `INPUT_INVALID`. The supplied request contained `ui_locales` and requested `openid` alongside the three Daclify scopes. The strict canonical request schema rejected the extra parameter; the scope validator separately rejected `openid`. Public requests with fresh synthetic state/challenge reproduced 400 both with and without the language hint. No real user's OAuth state, challenge, code, token or full request URL is stored in this evidence.

The HTTP boundary now ignores unrecognized query parameters, rejects duplicate parameters before normalization, and removes the additional `openid` scope before passing the request into the existing strict authorizer. Unsupported Daclify scopes, `openid`-only requests, repeated scopes, oversized fields, foreign client/callback/resource and invalid S256 PKCE remain refused. The persisted request contains only canonical Daclify fields. Token responses report the actual granted scopes; no OIDC identity grant, ID token, email or profile endpoint is added. The existing read/preview option still removes submission without a companion. Exact client registration and fresh account-control proof remain required.

This follows OAuth's treatment of unrecognized authorization parameters and scope narrowing in [RFC 6749, sections 3.1 and 3.3](https://www.rfc-editor.org/rfc/rfc6749). [OpenAI's authentication guidance](https://developers.openai.com/plugins/build/auth) supplies the client metadata, issuer/callback and PKCE contract. The fix changes the private HTTP boundary; the public core17/module24/MCP8 artifacts and all 140 frozen core SDK files remain byte-identical. No contract, migration, stored field or index changes.
