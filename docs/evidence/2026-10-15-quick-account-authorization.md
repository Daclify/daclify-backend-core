# Quick ballot account authorization foundation

15 October 2026. Local foundation for the [complete implementation plan](../superpowers/plans/2026-10-15-quick-ballots.md); the voting product and testnet launch remain incomplete.

The core-owned `quickauth` companion requires both a configured registration gateway and an actual account-key, native-active-permission or supported EVM signature. It forwards only the exact signed `respond`/`remove` bytes to the pinned Quick ballot source. Default-wallet changes require root control and incoming wallet consent. The canonical identity remains the same across default changes and registry cleanup; numeric registry IDs never authorize additional votes.

Requests bind chain, original runtime, companion authority, epoch/nonce and a maximum five-minute expiry. Submissions additionally bind source code hash, action, payload and the credential actually proved. Public schemas, ABI, table transport parsers, encoders, digests and release pins are generated/exported in the core SDK. No new API or account UI is enabled by this foundation.

The main runtime only adds bounded migration/source families 8 and 9. Adding authorization directly produced a 1,088,084-byte runtime rejected by Spring's 1 MiB transaction decoder. Moving it to the companion produces a deployable 1,047,804-byte runtime and an 83,452-byte companion using pinned CDT 4.1.1 `-O=s`. Native deployment succeeds without changing decoder limits. The runtime retains little size margin; further native changes must be measured before deployment.

`qaccounts` stores one identity commitment, one optional default, replay/epoch counters and deactivation time. Its sole secondary index enforces unique immutable anchors. No profile, membership graph or list of paired accounts is copied. `qcfg` stores source/gateway pins, capacity, current allocation count and the permanent numeric-ID high-water mark. Both families use existing operator-pool RAM metering and bounded migration scans. The 5,000-record testnet bound includes inactive records until permissionless cleanup after 30 days; cleanup batches contain at most 25 IDs.

Native measurements show 335 bytes per additional empty-default account, plus 112 bytes for the first table allocation; enabling native/EVM defaults adds 16/28 bytes. Successful measured actions consumed 522–1,409 microseconds apart from initialization. These local measurements are not target-chain capacity qualification or a 5,000-account load test. Exact hashes and measurements are in the [JSON evidence](2026-10-15-quick-account-authorization.json).

Verification: 28 focused unit/actual-WASM tests in six files; nine native authorization tests covering actual K1/native/EVM signatures, incoming consent, domain/nonce/epoch/target/context denial, capacity and revocation/reactivation; one portable native core27 upgrade/rollback test preserving raw DAO/member/executive rows and permissions. The five lifecycle tests include the exact 30-day cleanup boundary, atomic batch rollback, stable identity/high-water preservation and repeatable metering scans. Strict TypeScript passes.

The initial full core suite reported 1,042 passed and 17 failed in release-policy tests because the isolated worktrees had no builds. After generating builds, those policy tests correctly require a new matching companion artifact cohort; that coordinated package/manifest work remains task 6. The Docker observed-upgrade suite could not start without its owned resource fixture; it is not counted as passed. No live deployment, production publication qualification, custody qualification or independent cryptographic audit is claimed.
