# RAM observation and purchased credits — development

An authenticated active member can read `GET /v1/daos/:id/ram` for the exact configured deployment. Core/module rows come from the producer-owned `ramstats` and `ramalloc` schemas. Resources displays those per-payer counters and permanent settled purchase credits, alongside separately labelled whole-account quota/usage.

The reader pins the qualified runtime code/raw ABI and chain, reads complete bounded ledger/source/installed tables and checks each payer's current source code twice. Unknown/truncated coverage fails closed. Disabled observation never returns a zero-byte DAO estimate. A missing/mismatched approved payer source leaves the complete DAO total unknown. The public schema checks unique payers, aggregate counts and observation consistency; byte counts remain decimal strings through the UI.

Counters include instrumented core and module records in identity/recovery, activity, retained and platform categories. Shared meter metadata and other infrastructure are tracked separately; account-wide native usage also includes other DAOs, code, permissions and external system/token rows. A negative native quota is displayed as no finite reported quota, not free available capacity. These are live non-atomic reads with explicit start/end times, not billing snapshots or physical allocation attestations.

Purchased credits come only from permanent native `ramalloc` records created after actual verified quota acquisition. They do not expire with hosting arrears, and pruning does not sell them. The configured policy's included activity and member-slot values are targets, not issued capacity. Resources separately shows any issued `ramlimits` allocation. Observed new obligations preallocate bounded physical receipt holds, described below. Per-DAO growth enforcement and legacy adoption are in native qualification; public rollout remains gated. The Resources screen can quote and purchase permanent RAM with a connected Telos Zero wallet on a qualified finite-quota deployment. Card fulfillment uses the segregated reserve described below; public-chain/provider qualification and release/upgrade gates remain separate.

The owned Spring fixture tests reconcile instrumented native billing across core and all five modules. The reader's native test compares all six payer figures directly with `get_account` and verifies unchanged RAM usage/quota after the read. This qualifies the tested local observations, not a production allowance or public-chain deployment.

## Payer pools and issued allocations — development

The native operator can configure `setrampool` only with a current complete observer and a qualified finite system quota. The declared baseline covers code, permissions and untracked infrastructure; it is an operator attestation that must be reconciled to native usage. The pool retains separate platform headroom of at least 32 KiB. Its capacity test includes each DAO's greater of observed usage or issued/purchased bytes, plus shared platform counters and observer metadata. Checked integer sums and the actual payer quota prevent repeated grants from manufacturing physical capacity. The scan currently bounds a deployment to 5,000 DAOs.

`grantdaoram` issues activity, identity and completion budgets under a permanent per-DAO/payer/reference receipt. Exact retries do nothing; changed retry amounts are rejected. It requires at least 32 KiB completion budget and rejects an exhausted or changed payer pool. An allocation alone is not an obligation hold: observed new obligations additionally allocate their bounded physical receipt rows. No finite budget guarantees unlimited partial-withdrawal receipts. No subscription renewal automatically issues another grant. Per-DAO growth enforcement and the legacy adoption controller are in qualification.

A module payer needs its own actual RAM and its own owner's `bindrampool` action before the runtime can allocate it. Binding is permanent in this version and permits writes for exactly one runtime. Rebinding is rejected; writes for another runtime fail. This prevents two runtimes from pledging the same module account's free quota. Unbound module accounts can still serve separate runtimes without funded pools. Do not bind an existing shared module account until all other runtimes' executable work has been drained or migrated under their authorization; binding can otherwise block their writes. Never substitute surplus in the core account for RAM physically billed to a module.

Native checks qualify core pool conservation, exact retry/exhaustion, grant-metadata rollback at a tight pool boundary, and a separately bound Decide payer. Compiled tests exercise binding for all five modules. These checks do not certify complete allocation/enforcement or legacy migration. Root keys retain override/upgrade authority.

## Native RAM purchase

An active DAO member selects a current core or installed module payer and a minimum byte increase. The API quotes the pinned Telos RAM market, includes its native fee in the acquisition cost, then adds exactly the accepted resource policy's native operational markup (5% at launch). There is no Connect commission or extra conversion premium. A sponsor wallet need not be a DAO member; sponsorship grants no governance rights.

The UI requires explicit consent and sends the order and token payment in one wallet transaction. The contract binds its single bounded unpaid intent to that transaction ID; a separate later payment is rejected. Unpaid preparation never appends permanent order rows. Permanent records are created only inside a funded, atomic acquisition. The native callback verifies every receiver's actual quota increase before crediting permanent DAO RAM. Any failed leg, changed policy/source, expired order or unmet minimum rolls back all funding, acquisitions and credits. Estimates cannot guarantee a future market price. Both the byte minimum and payment ceiling are enforced on chain. Quotes last at most the configured lifetime, 300 seconds at launch.

The qualified system code and both semantically identical downloaded/re-encoded ABI hashes are explicit allowlists. Unmanaged `userres.ram_bytes + 1400` must match the RPC's finite account quota. Managed or unqualified modes are refused. Native acquisition was tested against real system WASM in the owned Spring fixture; public-chain release qualification remains required.

## Card funding and recovery

Card checkout snapshots the complete native acquisition cost, current 15-minute USD/TLOS rate, accepted resource policy and exact USD price. The card markup is 20% at launch with a $5 minimum total. It is an alternative to the native 5% fee, not an additional fee. Exact administrator consent requires session, CSRF and a fresh account-control proof. Quote, price, account and DAO inputs are validated again before preparing the idempotent Stripe checkout.

The card rail rejects test-mode Stripe configuration on mainnet; test payments cannot provision real mainnet RAM. Configure the separate RAM product, webhook destination, platform account ID and live-charge gate from the environment examples. Stripe callbacks queue reconciliation; the worker retrieves the actual checkout, successful payment intent and paid charge, rejects mismatched account/mode/currency/amount/metadata, partial or pending refunds and disputes. An unpaid or authenticated-pending checkout never buys RAM. Unknown provider state retries without assuming payment. A webhook generation received during a worker lease survives for another reconciliation pass.

Fund the runtime's segregated operator reserve by transferring actual eosio.token TLOS with exact memo `ramreserve`. This is an operator funding deposit, not a DAO donation and not a refund entitlement. The native `fulfilram` action requires the configured creation settler and debits only this reserve. It invokes the same all-receiver acquisition callback with zero native operational fee. Accepted card markup is retained in a parallel permanent receipt; fiat operational revenue is not booked as native treasury assets. DAO treasury, stakes and claims do not fund card RAM.

Each immutable SQL order has a full deployment domain, once-only native reference, exact approval/provider identity, checkout and payment references, and permanent acquired-byte/settlement evidence. Lost checkout responses can be recovered through signed events and fresh provider retrieval. Lost native responses are reconciled from an irreversible, code-qualified native receipt before any new purchase. Retry/replay cannot spend the reserve twice. Existing row layouts, signing domains and native receipt references are unchanged.

An insufficient reserve, changed policy, RPC/provider failure or stale deployment blocks provisioning. The worker retries boundedly, then flags review. An administrator can explicitly reconcile the saved order after the operator resolves the cause. A refund or dispute after acquisition flags review and blocks new card orders for that DAO; it never sells occupied RAM or revokes the acquired-byte receipt. Provider state and native transactions are not one atomic transaction: a refund can arrive during provisioning and must be reconciled afterward. Operator keys with root authority can always bypass contract accounting; keep active spending authority under reviewed contract/operating permissions.

The owned native fixture qualified reserve/DAO-liability conservation, exact acquisition, no stacked markup, authorization, replay and all-receiver rollback. PostgreSQL and the real Stripe SDK with synthetic HTTP qualified consent, immutable data, unknown response recovery, payment checks and worker fencing. These are not live Stripe or public-chain qualification. No production reserve was funded or card charge sent by these tests.

## Once-only included and member allocations

An operator can opt into `setramauto` after qualifying and funding every offered payer pool. The bounded offer list has at most six distinct payers, includes core, and splits exactly the current governed included activity budget across actual core/module accounts. Each offer has a separate completion budget of at least 32 KiB; this is allocated capacity, not yet an obligation-specific hold. A stale governed policy blocks new grants until the offers are explicitly reviewed and updated. Disabling the schedule uses an empty offer list.

Creating a new DAO under this schedule atomically creates permanent accepted-policy/slot markers and payer allocations. Failure of any backing check rolls creation and every allocation back. All free slots are allocated once, using the current free-member policy (10 when membership billing is not configured). Contract deployment by itself does not enable this schedule. Existing DAOs are not silently adopted or charged.

A verified `setcapacity` payment attestation grants only the increase above that DAO's maximum previously funded slots, at the original accepted identity rate. Exact retries, monthly renewals, slot replacement, expiry, cancellation and reactivation do not grant those bytes again or take occupied bytes away. Later global price/budget changes do not alter an existing DAO's accepted rate. Resource readout exposes this rate, policy revision and maximum funded slot count separately from current monthly membership entitlement. Root/operator authority must provision the real core RAM before increasing membership capacity.

## Accepted exhaustion policy and local enforcement

The user approved full-claim emergency withdrawals when ordinary DAO RAM is exhausted. Partial withdrawals require available ordinary RAM. Every partial exit adds a permanent financial receipt, so a fixed emergency reserve cannot guarantee arbitrarily many partial exits. The Treasury shortcut selects the exact full available balance. On observed new obligations, full withdrawal consumes ready receipt holds and partial withdrawal retains them. The reference-token native exhaustion test qualifies that physical-account path; the per-DAO guard also has local native exhaustion tests; public qualification remains gated.

Before enabling quotas, qualify per-obligation/ballot completion bounds, receipt retention, recipient token-row payer behavior, key recovery and cleanup across actual payer accounts. Preserve existing obligations, member nonces and encryption domains through bounded legacy backfill and protected mutation overlays. An allocation or dashboard counter alone is not that guarantee.

Native token transfers can create or change the payer of rows in a separate token contract. The [pinned official token calibration](evidence/2026-10-09-native-token-ram.json) measured 368 sender bytes on a first payout; recipient transfers/closure subsequently moved or freed those bytes without Daclify callbacks. Current metered-contract observations do not cover arbitrary token-row changes. Qualifying those external costs/ownership and bounded completion holds is required before enabling exhaustion enforcement. The normal six-payer population test did not settle native payouts.

## First-use metadata allocation

Newly enrolled human accounts allocate their fixed credential-epoch row immediately, just as agent accounts already did. First signing-key recovery then modifies existing fixed-size state. Newly accepted payroll schedules likewise allocate the fixed control row at commitment; first settlement updates its existing payout timestamp. These changes preserve original row serialization, identifiers, key/nonce domains and legacy fallback behavior. They remove two first-use allocation paths. The separate hold/adoption/guard code below has local tests; token-payer integration and remaining module lifecycle paths still need release qualification.

## Physically allocated obligation receipt holds — development

With observation enabled, accepting an obligation also creates a separate DAO-scoped `ramholds` row with 1,024 bytes of physical padding. This is real native RAM occupied before approval, not an unfunded counter or a premature payment receipt. Canonical packed receipt size, primary/index geometry and scope headers are checked on chain against the hold recipe. Cancellation releases the hold. Native settlement consumes it; settlement into an internal claim shrinks it to 512 bytes of padding and marks it ready for that recipient.

A full-claim withdrawal releases up to 25 ready obligation/legacy-claim holds before appending the withdrawal receipt. Partial withdrawals retain all claim holds and append ordinary receipts. If several obligations accumulated into one full withdrawal, unused ready holds can be cleared permissionlessly in batches of 1–25 with `clearholds`, only while the recipient has no outstanding claim. Pending obligations, financial receipts and balances cannot be removed by this action. Failed payment/withdrawal rolls every hold and liability mutation back.

Resources reports both `ramholds` and `ramclmholds` canonical serialized hold rows plus qualified primary/index/header overhead, already included in retained usage. The reader refuses more than 5,000 held rows rather than returning a partial total. These live reads are not atomic billing snapshots.

The sizing includes the 368-byte first-transfer headroom measured for the pinned official reference token; this does not qualify arbitrary token code, external row-payer changes or Telos production token behavior. These holds cover the runtime receipt path, not every module execution/election or private-key-grant path. New unobserved deployments and old obligations retain their existing settlement behavior. Legacy adoption is in controller qualification; external token reconciliation and quota enforcement remain release gates; no emergency execution guarantee is claimed yet.

## Bounded migration controller — development qualification

The shared write wrapper now has typed, bounded row/singleton backfill and temporary markers for protected changes before a scan. It includes primary key zero, avoids uint64 cursor overflow and releases markers after their row is scanned or deleted. Ordinary insert/growth/pruning is blocked while migration is active; permitted changes remain subject to authorization and actual native RAM. This kernel has compiled and native accounting tests, including singleton shrink and last-row headers.

The development controller provides operator-authorized begin, complete typed core/module family scans, bounded legacy obligation/claim and election-hold adoption, once-only physically backed inherited capacity and bounded sealing. RAM reports reject active migration. Exact source hashes, installed pins and pending executable plans are checked; no old approval is rewritten. Full backfill accepts unobserved legacy state. A separate completion-only adoption path adds missing holds/metadata to already metered deployments without recounting their historical rows. See [the bounded migration runbook](operations/ram-migration.md). Native qualification of the current controller, full supported-release lifecycle, token row-payer reconciliation and quotas remain release gates. Metadata and holds need actual purchased RAM; they are not an unlimited reserve.

## Per-DAO growth enforcement — development qualification

`setdaoquota(dao_id,enabled)` is an explicit native operator action. It refuses active migration, missing credentials/financial completion holds, missing module completion reserves, unqualified/unbacked payer pools and existing usage without an allocation or actual purchased credits. Activation calls the current pinned module’s readonly `checkquota` and rolls back if any module refuses. It records its small control row as platform meter overhead. Normal API startup does not enable quotas. Original data records, nonces and signing domains are unchanged.

All positive instrumented writes are capped at that DAO/payer's recorded identity + activity + completion + actual purchased bytes. New core and module wrappers also apply the narrower ordinary cap (identity + activity + purchased bytes) to ordinary growth. Stored physical holds remain included in used bytes; the check is conservative and does not offer those occupied bytes as free space. Explicit receipt/term/hold and resource-provisioning tables can use the additional completion budget, under the same finite total cap. Accepted physical holds remain the backing for their tested completion paths; this is not an unlimited write bypass.

A partial claim withdrawal checks ordinary room for its permanent receipt before changing the claim or transferring tokens. Full claims release their held rows before creating the receipt. Failed writes roll back the mutation, counters, nonce and financial state. A physically funded TLOS RAM purchase can use bounded provisioning metadata space at the ordinary limit, verify the actual quota increase and then permit new ordinary writes. A payer with actual purchased credits can write without an additional operator-issued free grant; those credits are not invented included capacity.

Resources reports the actual per-DAO flag. Active enforcement requires a complete qualified observer; otherwise the API refuses the report. This development flag does not certify arbitrary token row-payer behavior, all old-release/module completion paths or production provider funding. Root authorities retain upgrade/override powers. Complete exhaustion, recovery, provider and immutable-release checks remain rollout gates.

Observed Works acceptance also allocates two fixed document-reference slots per milestone before committing funds. An empty slot has document/version zero and protects no document; submission/review updates its existing row and indexes. Repeated revisions reuse those slots. Unobserved deployments retain their prior reference behavior. Bounded legacy `adoptwork` fills missing slots before sealing. These reservations cover references to existing documents; creating a new document or uploading new content still requires ordinary RAM/hosting capacity.

Already observed completion adoption uses `oldobs`/`oldclaims` cursors and module completion-only families with quota guards disabled; it never resets historical counters. Activation scans are capped at 5,000 rows per relevant family (Works checks only the target DAO’s projects/milestones). See the migration runbook for authorization, funding and pending-approval limits.
